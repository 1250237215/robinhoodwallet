# DeBot Social Bridge

This Manifest V3 extension uses the already signed-in `debot.ai` browser session to synchronize activity from the personal DeBot watchlist with a user-configured Radar deployment.

It does not read or export DeBot cookies, passwords, local storage, or `sub_token`. A page-world bridge calls DeBot's own authenticated social endpoints, normalizes the returned records, and sends only allowlisted activity, watchlist, heartbeat, and command-result fields to the Radar social API. Supported activity is post, reply, quote, repost, delete, follow, unfollow, name change, avatar change, and bio change. Each account can enable any combination of those behaviors in Radar; selecting none pauses that account without removing it from DeBot. Raw DeBot response objects are never uploaded.

## Local pairing

1. Open `chrome://extensions`, enable Developer mode, and load this directory as an unpacked extension.
2. Open the extension details and choose **Extension options**. Enter the Radar social API address, ending in `/api/social`, and the same random device token as `SOCIAL_BRIDGE_TOKEN` on the server.
3. Click **Save**. Chrome asks for access only to the hostname entered in the previous step. HTTPS is required except for `http://localhost` and `http://127.0.0.1` development servers.
4. Reload an already open Radar page so the newly registered content script can connect it to the extension.
5. Keep a signed-in DeBot tab open; it may remain in the background while using Radar. The extension badge shows `ON` after the first successful heartbeat.

Runtime settings are read only from browser-local extension storage. An existing `config.local.js` is migrated once when the options page opens and storage has not been configured yet. If its host permission was retained from an older installation, migration is automatic. Otherwise the options page stages the legacy values in memory and completes migration only after the user clicks **Save** and grants that exact host. The legacy file remains on disk, stays ignored by Git, and is never loaded by the service worker or exposed to website scripts.

The extension uses a 30-second recovery alarm to wake throttled background tabs, retry queued posts, and verify the DeBot page. A stalled post upload is abandoned after two seconds, then failed uploads retry after 2, 4, and 8 seconds; the alarm is the final fallback after that fast retry window. Longer-running DeBot analysis calls keep their separate timeout. The extension reuses an existing DeBot tab, creates one pinned background tab when none exists, and reloads an unresponsive bridge with bounded backoff. Sanitized posts are kept in a private bounded outbox until the Radar API explicitly acknowledges them. If the outbox reaches its 1,000-record or 4 MiB limit, already queued posts are preserved and the page retries new posts after older records drain. A temporary VPS or network outage therefore does not silently evict an earlier accepted post.

Live activity is captured from DeBot's personal-watchlist WebSocket immediately, including text and binary browser frames, with an independent one-second REST poll of the monitored-account timeline and the recovery alarm as fallbacks. After DeBot has authorized its own `portal-ws` connection, the bridge sends DeBot's standard personal-feed subscribe event on that already authorized connection. It never reads, stores, or forwards the authorization payload. Featured, hot, and all-account feeds are not collected. A primary REST request is abandoned after 1.5 seconds so one stalled response cannot recreate the old 20-second blind spot. Returning online, restoring a cached page, focusing the DeBot tab, or making it visible triggers an immediate coalesced primary poll. The newest 50 records are delivered before any recovery work; cursor-based historical recovery runs in an independent worker, fetches at most three older pages per pass, resumes its saved cursor after transient errors, and never blocks the next primary poll. Recovery stops at an already observed record or after 100 pages (5,000 records), so activity older than that bounded upstream window cannot be reconstructed after a very long outage. Each activity record carries the millisecond `discoveredAt` from its first browser observation; duplicates, batches, and upload retries preserve that original value. Follow, unfollow, profile, and delete records are accepted only when DeBot supplies a stable source timestamp, preventing a fallback poll from inventing repeated occurrences. Authentication failures mark the Radar connection unhealthy immediately. A transient newest-page timeout, network failure, or DeBot error remains diagnostic-only while an authorized portal WebSocket is active; without that live socket it must occur at least three consecutive times over at least eight seconds before the bridge reports an error. A successful newest-page poll clears that failure state immediately. An older-page recovery failure keeps its cursor for retry without marking the live lane unhealthy. The outbox protects every activity record the browser has already observed.

The Radar website remains passwordless. The device token authorizes only social watchlist and bridge API calls; public read-only social endpoints do not expose it. The extension has no default permission for arbitrary HTTPS sites. It requests one exact hostname when the user saves settings, dynamically registers `radar-content.js` for the matching Radar path, and removes that registration when permission is absent.

The configured device token is bound to the configured server origin. Changing scheme, hostname, or port requires entering the token again, and every upload rechecks both the binding and Chrome host permission before adding the Authorization header. Plain HTTP is rejected unless the hostname is exactly `localhost` or `127.0.0.1`; public IP addresses and lookalike hostnames are not accepted.
