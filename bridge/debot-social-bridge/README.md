# DeBot Social Bridge

This Manifest V3 extension uses the already signed-in `debot.ai` browser session to synchronize activity from the personal DeBot watchlist with Robinhood Radar.

It does not read or export DeBot cookies, passwords, local storage, or `sub_token`. A page-world bridge calls DeBot's own authenticated social endpoints, normalizes the returned records, and sends only allowlisted activity, watchlist, heartbeat, and command-result fields to the Radar social API. Supported activity is post, reply, quote, repost, delete, follow, unfollow, name change, avatar change, and bio change. Each account can enable any combination of those behaviors in Radar; selecting none pauses that account without removing it from DeBot. Raw DeBot response objects are never uploaded.

## Local pairing

1. Open `chrome://extensions`, enable Developer mode, and load this directory as an unpacked extension.
2. Open the extension details and choose **Extension options**. Enter the Radar social API address and the same random device token as `SOCIAL_BRIDGE_TOKEN` on the VPS.
3. Keep a signed-in DeBot tab open; it may remain in the background while using Radar. The extension badge shows `ON` after the first successful heartbeat.

Runtime settings are read only from browser-local extension storage. An existing `config.local.js` is migrated once when the options page opens and storage has not been configured yet. That legacy file remains on disk, stays ignored by Git, and is never loaded by the service worker or exposed to website scripts.

The extension uses a 30-second recovery alarm to wake throttled background tabs, retry queued posts, and verify the DeBot page. A stalled post upload is abandoned after two seconds, then failed uploads retry after 2, 4, and 8 seconds; the alarm is the final fallback after that fast retry window. Longer-running DeBot analysis calls keep their separate timeout. The extension reuses an existing DeBot tab, creates one pinned background tab when none exists, and reloads an unresponsive bridge with bounded backoff. Sanitized posts are kept in a private bounded outbox until the Radar API explicitly acknowledges them. If the outbox reaches its 1,000-record or 4 MiB limit, already queued posts are preserved and the page retries new posts after older records drain. A temporary VPS or network outage therefore does not silently evict an earlier accepted post.

Live activity is captured from DeBot's personal-watchlist WebSocket immediately, including text and binary browser frames, with an independent two-second REST poll of the monitored-account timeline and the recovery alarm as fallbacks. Featured, hot, and all-account feeds are not collected. A primary REST request is abandoned after 3.5 seconds so one stalled response cannot recreate the old 20-second blind spot. Returning online, restoring a cached page, focusing the DeBot tab, or making it visible triggers an immediate coalesced primary poll. The newest 50 records are delivered before any recovery work; cursor-based historical recovery runs in an independent worker, fetches at most three older pages per pass, resumes its saved cursor after transient errors, and never blocks the next primary poll. Recovery stops at an already observed record or after 100 pages (5,000 records), so activity older than that bounded upstream window cannot be reconstructed after a very long outage. Each activity record carries the millisecond `discoveredAt` from its first browser observation; duplicates, batches, and upload retries preserve that original value. Follow, unfollow, profile, and delete records are accepted only when DeBot supplies a stable source timestamp, preventing a fallback poll from inventing repeated occurrences. Any failed newest-page poll marks the Radar connection as unhealthy until a complete primary poll succeeds; an older-page recovery failure keeps its cursor for retry without marking the live lane unhealthy. The outbox protects every activity record the browser has already observed.

The Radar website remains passwordless. The device token authorizes only social watchlist and bridge API calls; public read-only social endpoints do not expose it. The legacy plain-HTTP IP page is read-only and clears any old browser-local pairing token during initialization. Watchlist changes require the trusted HTTPS Radar page.

The configured social API base is restricted to the Radar HTTPS hostname, so the bearer device token is never sent over plaintext HTTP or to DeBot or an unrelated origin. The original passwordless HTTP Radar page remains supported as a user interface and does not receive the device token.
